# QA Test - 2026-06-30

## Readiness Standard

This report uses the private-app standard: Anime Ongaku is for 3-5 trusted friends, not a public SaaS product. "Production ready" means the app is smooth for real users and does not regress important pre-server behavior: sign-in, sync, browsing, playback, queue actions, downloads, offline playback, playlists, and understandable recovery when something goes wrong.

This report intentionally does not treat these as release blockers by themselves:

- Public-app security hardening beyond a basic/private-app standard.
- Load balancing, scaling, or high-concurrency behavior.
- Fresh-install migration risk from old signing/data, since everyone can start fresh.
- Use of Media3 unstable APIs.
- Lint warnings that do not affect shipped behavior.
- Perfect admin/operator tooling.

## Private Rollout Decision

The server-backed app is close to usable for a private friend rollout, but I would not hand it to friends yet. The core path works on a real device, but there are still user-facing smoothness and regression risks that should be fixed or retested first:

1. First-run sync appeared empty until app restart.
2. Bottom sheets could trap navigation during QA.
3. Queue/menu actions were visible but not fully exercised end-to-end on device.
4. Release/server URL setup needs one clear private-distribution path.
5. Kitsu token refresh needs to work before users keep the app installed for ongoing sync.

After those are fixed or explicitly accepted, this should be reasonable to share as a private beta.

## Fix Before Giving To Friends

### 1. First-run sync should not require restart

Evidence: after successful login, Home showed an empty "sync your library" state while server jobs were still finishing. After force-stop/restart, Home showed quick picks and Library showed populated counts.

Why it matters: this is likely the first impression for every friend. If the app looks empty after login, they will think it failed even if the server is still working.

Expected behavior:

- After login, show an obvious sync-in-progress state.
- When server sync finishes, pull the library automatically.
- Home and Library should populate without force-stopping the app.
- If sync fails, show a clear retry path.

Suggested validation:

1. Fresh install.
2. Sign in.
3. Wait for server sync completion.
4. Confirm Home/Library update without restarting.

### 2. Bottom sheets should reliably dismiss

Evidence: during QA, the Now Playing sheet and a compact track action sheet stayed open after Back, scrim taps, visible close taps, and swipe-down attempts. Force-stop was the reliable recovery.

Artifacts:

- `17b-home-after-close.*`
- `19-main-after-drag.*`
- `31-settings.*`
- `33-settings-after-sheet-dismiss-attempt.*`

Why it matters: if this reproduces by normal touch, users can get stuck and lose access to navigation/settings.

Expected behavior:

- Back closes the active sheet.
- Scrim tap closes modal sheets where appropriate.
- Close button closes the sheet.
- Swipe-down works for draggable bottom sheets.

Suggested validation:

- Retest with physical touch, not only adb.
- Test Now Playing, track action sheet, Save to Playlist sheet, and any download management sheets.

### 3. Queue and action-menu behavior needs end-to-end device QA

Evidence: the menu actions rendered, and unit tests passed, but device QA did not fully execute each action.

Why it matters: queue behavior is one of the app's core features. It existed before the server rewrite and should not regress.

Actions to test on device:

- `Play next` while a queue is already playing.
- `Add to queue` while a queue is already playing.
- `Replace queue`.
- Multi-song Play/Shuffle from Library.
- Duplicate song entries: add the same song multiple times and confirm distinct queue entries.
- Like/unlike updates Liked Songs.
- Save to playlist creates or updates the expected playlist.
- Queue survives app restart.
- Mini-player Next updates the queue and metadata correctly.

Expected behavior:

- Queue entries keep their own identity.
- Duplicate songs can exist as separate queue entries.
- Play Next inserts after current.
- Add to Queue appends.
- Replace Queue replaces only when explicitly requested.

### 4. Private distribution must have one clear server URL path

Evidence: the tested debug build worked because `ONGAKU_SERVER_BASE_URL` was compiled as `http://192.168.68.85:8080/`. Current release/onboarding paths can block sign-in if the server URL is empty and the user has no visible setup path.

Why it matters: for friends, the app should either just work or tell them exactly what to do. They should not need to know build flags.

Acceptable private-app solutions:

- Always distribute builds with the server URL compiled in.
- Or expose Server Settings on first launch in release builds.
- Or fail release builds if `ONGAKU_SERVER_BASE_URL` is missing.

Suggested validation:

- Install the exact APK that friends will receive.
- Confirm Settings shows the expected server URL.
- Confirm a fresh user can sign in without hidden debug-only steps.

### 5. Kitsu token refresh should work for ongoing usage

Evidence: server sync currently reads the stored access token in `server/src/sync/librarySyncPipeline.ts`; the review found refresh-token support exists but is not used by the sync pipeline before Kitsu calls.

Why it matters: even for 3-5 friends, the app should not silently stop syncing after a token expires.

Expected behavior:

- If the access token expires, the server refreshes it.
- If refresh fails, the app clearly asks the user to sign in again.
- Sync jobs do not loop forever or fail silently.

Suggested validation:

- Add a test for expired access token with valid refresh token.
- Add a manual/seeded test for refresh failure and reauth messaging.

## Fix Soon For A Smooth Private Beta

### 6. Pending writes should not disappear after failures

Review concern: pending write flushing can report success even when the flush failed.

Why it matters: playlist/library edits made during flaky network periods should not vanish.

Expected behavior:

- Failed writes remain pending or show a clear failed state.
- WorkManager retries when the server is unavailable.
- Users can recover without recreating edits manually.

### 7. Playlist flows need a real user pass

The Library showed auto playlists correctly, and the Save to Playlist action was visible, but full playlist creation/edit/delete behavior was not exercised during this QA run.

Test:

- Create playlist.
- Add song from action menu.
- Remove song.
- Rename playlist if supported.
- Restart app.
- Confirm server and local state agree.

### 8. Offline mode should cover more than completed playback

Verified: a completed download played while the API container was stopped.

Still unverified:

- Download starts, server drops, then download resumes/retries.
- Airplane-mode playback from a cold app start.
- Offline playlist/like edits queue and later sync.
- Clear message when trying to stream non-downloaded songs offline.

### 9. Bluetooth/lock-screen artwork should be checked

Evidence: logcat showed SystemUI warnings for invalid album-art URI during playback.

Why it matters: this app is music-first. Artwork and metadata on lock screen, Bluetooth, and car receivers are part of the experience.

Test:

- Lock screen artwork.
- Bluetooth metadata.
- Car/Tesla receiver if available.
- Rapid skip through several tracks.

### 10. Connectivity error messages should be friend-readable

Evidence: the test phone had a stale Wi-Fi proxy, which broke sign-in until removed.

Why it matters: friends may be on VPNs, proxies, guest Wi-Fi, cellular-only, or a network that cannot reach the server.

Expected behavior:

- Sign-in failure distinguishes bad credentials from cannot reach server.
- Settings has a "test server connection" or equivalent diagnostic.
- Error text includes the configured server host.

## Accept Or Defer For This Private App

These are real findings, but they should not block a private friend rollout unless they conflict with the chosen distribution/deployment setup.

### Media3 unstable API lint errors

`lintDebug` fails because Media3 APIs need explicit `@OptIn` annotations. This is worth fixing because it is cheap and keeps checks green, but using unstable Media3 APIs is not itself a private-app production blocker.

### Stub auth Docker default

`server/docker-compose.yml` defaults `KITSU_AUTH_MODE` to `stub`. For a private app, this is acceptable if deployment docs/env are controlled and the real server uses `KITSU_AUTH_MODE=real`. It is still worth changing later to avoid operator mistakes.

### Admin job routes

Authenticated users can inspect/retry jobs. For 3-5 trusted friends on a private server, this is not a release blocker if the routes are not exposed casually. Minimal standard: do not show these routes in the app UI, avoid logging secrets, and keep the server private.

### Legacy encrypted preference migration

Not a blocker because everyone can start fresh and reinstalling/wiping data is acceptable for this rollout.

### Load, scaling, and queue worker cancellation

Not a blocker for 3-5 users. Revisit if media jobs pile up, the server gets slow, or duplicate background work becomes visible.

### `/healthz` media-root strictness

Useful operator hardening, not a friend-experience blocker as long as media playback/downloads are manually verified after deployment.

### Dependency audit and repo hygiene

Dev dependency advisories, generated log whitespace, and read-only Android SDK noise are cleanup tasks, not user-readiness blockers.

### One-device coverage

Only Pixel 7 Pro / Android 16 was tested. For a private rollout, this is acceptable if the friends use similar Android versions. Test one additional friend phone before calling the beta stable.
